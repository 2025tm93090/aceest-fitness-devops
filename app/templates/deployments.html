1. Rolling Update (Default Zero-Downtime) Active Standard

Incrementally replaces running application pods with new version pods using Kubernetes Deployment parameters maxSurge: 1 and maxUnavailable: 0. Ensures continuous availability during fitness class peak hours.

Pod Lifecycle Transition:
Pod v1 (Running) Pod v2 (Starting) Pod v2 (Ready) Pod v1 (Terminating)
Manifest: k8s/02-rolling-update.yaml
Rollback Command: kubectl rollout undo deployment/aceest-app
2. Blue-Green Deployment Atomic Switch

Maintains two identical production environments: Blue (Active) and Green (Staging/New Version). Traffic is routed via a single Kubernetes Service selector switch, achieving zero-downtime release and instant rollback.

3. Canary Release Progressive Risk Reduction

Routes a small percentage (e.g. 10% - 20%) of real gym user traffic to the new version canary pods while maintaining 80% on stable. Metrics and error rates are monitored before routing 100% traffic.

Stable v1 (80% Traffic) Canary v2 (20% Traffic)
4 Pods (80%)
1 Pod (20%)
Manifest: k8s/04-canary.yaml
Traffic split via Pod replica ratios or NGINX Ingress annotations.
4. A/B Testing Data-Driven Experimentation

Routes user requests based on HTTP request headers (e.g. X-Experiment: variant-b) or session cookies to evaluate conversion on the new AI workout recommendation engine versus traditional program lists.

Layer 7 Ingress Traffic Routing:
  • Variant A (Control): Standard Program Catalog (General traffic)
  • Variant B (Treatment): AI Personalized Program Engine (Tagged Users)
Manifest: k8s/05-ab-testing.yaml (NGINX Ingress Header Matching)
5. Shadow Deployment (Traffic Mirroring) Zero User Impact

Duplicates incoming production requests in real-time and forwards a mirror copy to the shadow version deployment without returning shadow responses to end users. Validates peak load performance, database query latency, and concurrency stability before official release.
